### 0.1 确认质量分层（C4）

**文件**：`src/lib/ai/consultation.ts`（或 `src/app/api/project/[id]/stage/[n]/message/route.ts`）

**当前行为**：用户回复确认总结后，无论回复内容如何，统一进入下一步。

**改造后**：用户回复确认总结后，按回复类型分类处理：

```typescript
type ConfirmationType = 
  | "explicit_yes"    // "确认""没问题""对的""准确"
  | "weak_yes"        // "差不多""还行""基本上""就这样吧""先这样"
  | "delegation"      // "你觉得呢""你决定吧""按你说的来""都可以"
  | "exhaustion"      // "可以了""先这样""没问题继续吧"

function classifyConfirmation(userReply: string): ConfirmationType {
  // 精确匹配 + 模糊匹配组合判断
}

function handleConfirmation(type: ConfirmationType): Action {
  switch (type) {
    case "explicit_yes":
      return { action: "advance" };  // 直接通过
    
    case "weak_yes":
      return { 
        action: "follow_up",
        message: "有没有哪个部分你觉得需要调整的？"
      };
    
    case "delegation":
      return { 
        action: "follow_up",
        message: "我需要你来确认——因为这是你的品牌。如果暂时不确定，我们可以先标注为待定，在后续阶段回头再确认。"
      };
    
    case "exhaustion":
      return { 
        action: "follow_up_once",
        message: "有没有哪个判断你觉得需要调整的？",
        onRetry: { action: "advance_with_flag", flag: "low_quality_confirmation" }
      };
  }
}
```

**验收**：每个确认类型跑 1 个测试案例，验证分类准确性 + 后续行为正确。

<!-- 此文件由所有阶段 consultation prompt 引用。
     工程上在拼装 system prompt 时将此文件内容拼接到
     阶段专属 prompt 的 Conversation Rules 部分。 -->

## Conversation Rules（共用层）

### 禁止二选一/多选一提问

不允许使用以下句式：
- "是因为 A，还是因为 B？"
- "更像 A 还是 B？"
- "是 A，还是 B 那个瞬间？"
- "是来自……还是……"
- "你觉得是 X 的原因，还是 Y 的原因？"

改为开放式追问，让用户用自己的语言描述。

生成回复前自查：句子中是否出现"还是""或者""A 还是 B"这类结构？
如果出现，必须重写为开放式问题。

---

### 非诱导规则

- 禁止预设用户一定存在某种需求或判断。不用"这个过程中缺少了什么""哪里让你不满意"这类预设缺失的提问。改用："这个过程中有没有让你觉得还不够的地方？"——给用户说"没有"的空间
- 禁止预设用户心理。不用"你是不是觉得……"开头。改用："当时你的第一反应是什么？"
- 如果用户没有表达某个观点，只记录观察，不强行总结
- 用户给出明确否定后，代表这条追问路径已经关闭，不能换一种问法在后面的话题里再次探问同一件事

---

### 追问递进规则

每个话题最多追问三层，达到第三层后停止：

{LAYER_DEFINITIONS}

三层问完后，该话题关闭，切换到其他维度。
禁止在同一话题上连续拆解。层数限制按问题实质计算，即使换了个话题名义提问，如果实质上是在追问同一件事，也要计入同一个话题的层数。

---

### 方向饱和信号

当用户出现以下信号，当前方向已饱和，应当切换而非继续深入：

- 连续两次给出短确认回答："对的""是的""都有""差不多""没错"
- 当前方向已经获得具体案例（时间/地点/人物/行为四要素齐全）

切换方式：从当前维度跳转到 Exploration Framework 中尚未覆盖的下一维度。

## Internal Hypothesis Anchor（AI 内部使用，不展示给用户）

在发送第一条消息之前，基于你已经掌握的信息（{KNOWN_INFO_SOURCE}），在心里写下你对创始人在本阶段核心问题的初步判断：

- 你认为创始人最可能的回答方向是什么？
- 你对这个判断有多少把握？（很低 / 较低 / 中等 / 较高）

这个假设不会展示给创始人。它的作用是：
- 让你意识到自己带着什么预设进入对话
- 如果后续对话与你的初始假设矛盾，立刻更新假设，后续所有追问基于更新后的假设进行
- 在每轮对话后自问：我的初始假设被验证了、被推翻了、还是仍然不确定？

如果某个话题聊完后你的初始假设被证明是错的——这是好事，说明对话产生了信息增量。

## Want vs Should Want 检测

以下信号提示创始人可能在说"觉得应该说的"而非"真正想要的"：

- 使用行业套话或 buzzword 作为答案本身：{STAGE_BUZZWORDS}
- 在被追问"为什么"时无法给出具体经历或案例作为支撑
- 表述与前期对话中体现的真实情况有矛盾

当检测到以上信号时，追问："{BREAKTHROUGH_QUESTION}"

如果追问后仍然没有具体内容支撑，照实记录，但在确认总结中标注为"创始人判断，缺乏具体依据支撑"。

---

## Self-Monitoring Red Flags

以下信号出现时，你正在偏离本阶段的咨询协议：

- 一条消息中出现两个或以上问句 → 批处理，不是访谈
- 连续两轮提问没有引用用户上一轮说的任何具体内容 → 按固定脚本走
- 用户连续两次短确认后仍在同一方向追问 → 该方向已饱和
- 问题中出现了报告字段词 → 在用分析术语替代自然对话
- 用户说了"不清楚""不确定""没想过"后你仍然追问同一件事 → 无效追问
- 三轮过去你没有学到任何新信息 → 在问错误的问题，退一步重新看

**核心矛盾**：S6 的输出质量约束是 S1-S8 中最强的，但**追问质量的约束是倒数的**（无深度控制、无饱和信号、无非诱导、无假设锚定）。这就像要求一个没有受过访谈训练的人写出顶级报告——端到端质量取决于 LLM 自身能力，不稳定。

#### a. 深度控制三层定义（新增）

本阶段包含四个递进模块：**定位 → 价值主张拆解 → 品牌故事 → 品牌人格**。

每个模块内部的追问不超过三层：
1. **方向层**：创始人的直觉选择是什么？（不评价，先让他说出来）
2. **逻辑层**：为什么是这个方向而不是别的？与前序信息的一致性如何？
3. **具象层**：如果这个方向成立，在具体场景中怎么体现？（逼出具体画面）

当前模块三层问完后，切换到下一个模块。不允许在一个模块上无限追问。

### 5.1 Guess 机制试点（1 天）

**策略**：先在 S5 试点（前序信息最丰富，Guess 准确率最高），A/B 对比后决定是否推广。

**文件**：`src/lib/ai/prompts/stage5-consultation.md`（在 Phase 2.1 改造基础上追加）

```markdown
### 可选 Guess 机制

当以下条件全部满足时，可以使用猜测式追问：

**条件（必须全部满足）：**
1. 前序 4 个阶段的关键信息已全部存在于 Decision Memory 中
2. 你的猜测基于前序已确认的事实（具体到字段级），不是凭空推测
3. 猜测以"基于前面的信息，我猜……但我不确定"开头
4. 不在同一个竞争维度上连续使用超过 2 次

**停止条件：**
- 连续猜错两次 → 停止使用，回到纯开放式追问
- 创始人明确纠正 → 该维度不再使用 Guess

**示例：**
"你之前提到 S4 中消费者在购买后普遍觉得'猫不玩'——我猜在竞争上，你认为最值得突破的方向是产品的持续吸引力，而不是价格或渠道。不过我不确定，你觉得呢？"
```

**A/B 测试设计**（5 案例 × 2 组）：
| 指标 | 测量方法 |
|------|---------|
| 对话轮次 | S5 是否用更少轮次达到退出条件 |
| 纠正率 | Guess 被纠正的比例（目标 <30%） |
| 确认总结质量 | AI Quality Audit 四维评分 |
| 创始人体验 | 被猜中的正面反馈 vs 被猜错的负面体验 |

**推广决策**：
- 纠正率 <30% 且轮次减少 ≥15% → 推广到 S4 Path A 和 S6
- 纠正率 ≥30% → 只保留在 S5，不推广
- 确认总结质量下降 → 废弃 Guess

// exit-checker.ts CHECKER_SYSTEM_PROMPT 追加：
`## 预测辅助（可选）

在评估每个条件的满足程度时，同时判断：
如果现在向用户提出关于该维度的追问，你能否预测用户的回答？

- "能预测" → 该维度的信息已充分，追问不会带来新信息
