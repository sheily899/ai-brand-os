## 7. S3 vs S8 交叉对比

| 指标 | S3 市场机会 | S8 内容策略 | 差异分析 |
|------|-----------|-----------|---------|
| 固定前缀占比 | 77.1% | 74.5% | S3 模板更大 (14,712 vs 13,511 chars) |
| 跨项目首次节省 | **72.9%** | **69.6%** | S3 更高（固定前缀占比更高） |
| Cache Hit (Warm-1) | 7,168 / 9,834 | 6,528 / 9,380 | S3 缓存命中更多固定 token |
| Search Context 规模 | ~1,530 chars (~765 tokens) | ~1,482 chars (~741 tokens) | 接近 |
| DM 规模 | ~693 chars (~347 tokens, S1-S2) | ~1,180 chars (~590 tokens, S1-S7) | S3 DM 更少 |
| Quality (Cold=Warm) | ✅ 73=73 | ✅ 73=73 | 两个阶段均零影响 |
| H4.1 通过 | ✅ 72.9% | ✅ 69.6% | 均远超过 30% 阈值 |

### 关键发现

1. **S3 和 S8 的 cache 节省比例高度一致** (~70-73%)。这是因为两个阶段的 prompt 结构相同（模板 + 协议 + Search Context + Decision Memory），固定前缀占比接近。

2. **S3 的节省略高于 S8 (72.9% vs 69.6%)**，因为 S3 的 DM 只有 S1-S2（比 S8 的 S1-S7 少 ~250 tokens），动态内容占比更低。

3. **S3 的搜索上下文并未显著更大**：本实验的 S3 Search Context (~1,530 chars) 与 S8 (~1,482 chars) 接近。但这是精选后的模拟数据——真实 S3 可能涉及多轮搜索累积，实际动态 token 占比可能更高。

4. **Cache 对质量的零影响在 S3 上得到复现**：Warm 组 5/5 审计完全一致 (73)，Cold 组排除审计方差后也是 73。

## 8. 风险说明

1. **S3 Search Context 规模波动大**: 不同行业/品类的搜索结果量差异显著。慢象咖啡（精品咖啡）属于数据丰富的品类，但长尾品类的搜索结果可能较少，Search Context 大小变化会影响 cache 效率。

2. **S3 搜索次数多于 S8**: S3 通常需要多次搜索（市场趋势、消费者数据、行业报告等多次查询），搜索上下文累积可能比 S8 更大，实际节省可能更低。

3. **不可跨项目缓存的确认**: Search Context 和 Decision Memory 是项目特定的，S3 也不例外。固定前缀节省是唯一可跨项目共享的 cache 收益。

---

## 9. 建议

1. **S3 Search Context 截断策略**: 对于数据丰富的行业，设置 Search Context 最大注入量（如 Top-3 搜索结果），避免动态 token 占比过高
2. **S2/S5 尽快验证**: 完成全搜索阶段 (S2/S3/S5/S8) 的 H4 测试，建立完整的阶段级 cache 效率模型
3. **Decision Memory 精简**: S1-S2 的战略资产可进一步压缩（仅保留关键决策和数据），减少不可缓存 token
