## 三、发现的问题

### P0 — 阻断性问题

*无 P0 问题。全流程可完整运行，无崩溃或数据丢失。*

### P1 — 重要问题

#### 问题 1: 审计评分无法有效区分输入质量

**复现步骤**:
1. Case 1（资深调香师，有调研有数据）→ S6 得分 100
2. Case 2（应届生，无调研无经验）→ S6 得分 100

**实际结果**: 两个质量差异极大的案例在 S6 均获得满分 100。Case 1 平均分 85.1，Case 2 平均分 82.6，仅差 2.5 分。Case 2 的 S2 (93) 甚至高于 Case 1 的 S2 (87)。

**预期结果**: 低质量案例应有显著更低的审计分数（至少 10-20 分差距），S6 不应在两种情况下都满分。

**严重程度**: P1  
**修复建议**: 
- 调整 AI Quality Audit 的评分 Prompt，引入更严格的基准线
- 对 S6 增加"必引前序阶段具体判断"的硬性检查
- 引入"信息充分度"作为评分子维度

#### 问题 2: Evidence 维度评分过于宽松

**复现步骤**: Case 2 的创始人在 S1-S5 中反复表示"不太清楚"、"没做过调研"、"不了解市场规模"，但其 S2 evidence 仍得 4 分。

**实际结果**: 
| Stage | Case 1 Evidence | Case 2 Evidence |
|-------|----------------|----------------|
| S1 | 4 | 3 |
| S2 | 4 | 4 |
| S3 | 4 | 3 |
| S4 | 3 | 3 |
| S5 | 3 | 3 |
| S6 | 5 | 5 |

Case 2 的 S2 和 S6 获得与 Case 1 相同的 evidence 评分（4 和 5），尽管没有任何实际数据支撑。

**预期结果**: 无数据来源的结论应得到 evidence ≤ 2 分。

**严重程度**: P1  
**修复建议**: 
- Evidence 评分增加 dataSources 字段检查：0条来源 → 自动 ≤2 分
- 区分"创始人声称"与"可验证事实"的证据等级

#### 问题 3: Cross Stage Context Check Layer B 未触发

**复现步骤**: 在 Case 1 S5 和 S6 的审计中，crossStage 的 layerB issues 均为 0。

**实际结果**: 跨阶段语义检查（Cross Stage Context Check Layer B）在所有阶段的审计中均未发现任何问题。

**预期结果**: 至少应在部分阶段发现"引用但未深化"或"语义偏移"的问题。

**严重程度**: P1  
**修复建议**: 
- 验证 Layer B 的触发条件是否过于严格
- 检查 AI Quality Audit system prompt 末尾的 Strategic Continuity 段是否被正确注入
- 增加 Log 输出来追踪 Layer B 是否被执行

### P2 — 中等问题

#### 问题 4: Smart Optimize 后阶段卡在 waiting_confirm

**复现步骤**: Case 2 S2/S3/S4/S5/S8 触发 reoptimize → Smart Optimize 成功执行 → 阶段状态变为 `waiting_confirm`，不再自动推进。

**实际结果**: 两个案例共 11 个阶段中，有 10 个处于 `waiting_confirm` 状态（并未真正完成的 StageRecord）。

**预期结果**: Smart Optimize 成功后应自动重新审计并推进，或至少提供清晰的"确认此版本"入口。

**严重程度**: P2  
**修复建议**: 
- Smart Optimize 流程末尾自动调用 advance（重新审计）
- 或在 optimize API 响应中返回新的 gateDecision，前端据此提示用户

#### 问题 5: 搜索查询重复性高

**复现步骤**: 在 S3、S5、S8 中，连续多轮的搜索查询几乎相同（如多次 `site:iresearch.cn 中国香水 行业报告 2025`）。

**实际结果**: 同一阶段的多次搜索返回类似结果，没有基于当前对话内容调整搜索意图。

**预期结果**: 搜索意图应随对话深入而变化（从宏观市场 → 细分品类 → 具体消费者行为）。

**严重程度**: P2  
**修复建议**: 
- 搜索查询生成考虑当前轮次上下文
- 引入"搜索去重"机制避免重复查询

#### 问题 6: 阶段轮次与信息深度不匹配

**复现步骤**: Case 1（信息量大，每次回答 200-500 字）用了 4-5 轮/阶段，Case 2（信息量小，每次 50-150 字）用了 3 轮/阶段。

**实际结果**: AI 未因 Case 2 信息不充分而增加追问轮次。

**预期结果**: 信息不足时应增加追问轮次，而不是提前进入收敛。

**严重程度**: P2  
**修复建议**: 
- 在 consultation prompt 中增加"信息充分度自检"机制
- 收敛前评估是否已覆盖该阶段所有必填字段

### P3 — 优化建议

#### 问题 7: Audit 分数的终端展示不正确

**复现步骤**: 测试脚本中所有阶段的 `advanceResult.score` 和 `advanceResult.totalScore` 均为 `undefined`。

**实际结果**: 得分实际存储在 `auditReport.aiAudit.totalScore` 中，但 advance API 响应中未包含顶层的 `score` 字段。

**严重程度**: P3  
**修复建议**: 
- advance API 响应增加 `score` 和 `dimensions` 的顶层字段
- 或更新前端代码从 `auditReport.aiAudit` 路径读取

#### 问题 8: 部分阶段 structuredOutput 未持久化

**复现步骤**: GET stage API 返回的 `structuredOutput` 为 null，尽管 converge 成功。

**实际结果**: Stage 数据中无法通过 API 查看结构化输出内容。

**严重程度**: P3  
**修复建议**: 检查 `saveStructuredOutput` 的调用时机是否在 converge → advance 之间正确执行。

## 四、产品体验评价

### 4.1 咨询体验

**AI 咨询能力强项：**
- ✅ **一次一问**：两个案例 64 轮对话中，AI 严格遵守一次只问一个问题的规则
- ✅ **深度追问**：AI 善于从模糊回答中提取具体细节，如 Case 2 S1 追问"你卡住的地方，具体是哪些问题让你觉得写不下去"
- ✅ **主动开场**：项目创建后自动发送开场消息，承担咨询顾问角色
- ✅ **上下文记忆**：后续阶段能引用前序对话中的具体信息
- ✅ **不评判态度**：面对 Case 2 的不成熟回答，AI 保持专业引导而非批评

**AI 咨询能力待改进：**
- ⚠️ **信息充分度判断缺失**：AI 不会因信息不足而增加追问轮次，3-4 轮后直接收敛
- ⚠️ **搜索时机固定**：搜索仅按阶段触发(S3/S5/S8)，而非按信息需求触发

### 4.2 战略连续性

**表现良好：**
- ✅ **Decision Memory** 正确跨阶段传递（76 和 71 条战略资产）
- ✅ **S6 输出**引用了 S3/S4/S5 的具体发现
- ✅ **Backtrack** 正确影响所有下游阶段

**存在不足：**
- ⚠️ **S6 满分过于容易**——两种极端案例都获满分，无法区分推导质量
- ⚠️ **Cross Stage Check Layer B** 未发现任何阶段间语义断裂——可能过于宽松

### 4.3 整体评价

**像一个品牌咨询顾问吗？**  
部分像。AI 在对话中表现出了顾问式的追问和引导能力。但收敛时机过于固定，不会根据信息充分度灵活调整。

**有连续战略推理吗？**  
有。Decision Memory 和 S6 的引用结构证明了阶段间信息传递的连续性。但 Layer B 未触发说明语义层面的连续性检查还不够。

**容易理解下一步吗？**  
基本清晰。阶段导航和 gate decision 提供了明确的方向。但 `waiting_confirm` 状态的处理不够直观。

**存在割裂感吗？**  
存在几处割裂：Smart Optimize 执行后用户不知道下一步该做什么；搜索查询与对话深度的脱节；审计评分与实际质量的脱节。

## 六、结论

**AI Brand OS 的核心链路（S1→S8 + Audit + Smart Optimize + Backtrack）已完整可用。** 两个测试案例均成功走完全部 8 个阶段，没有出现链路断裂或系统崩溃。

**关键验证项：**
1. ✅ AI 能胜任品牌咨询顾问角色（一次一问、深度追问、主动引导）
2. ✅ 8 阶段间 Decision Memory 正确传递（147 条战略资产跨 2 个案例）
3. ✅ Audit Engine 正确运行（四维评分、Rule Check、Gate Decision）
4. ✅ Smart Optimize 闭环可用（6 次成功优化）
5. ✅ Backtrack 正确影响下游（5 个阶段 invalidated）
6. ⚠️ 审计评分区分度不足——这是当前最需要改进的方向

**下一步建议：**
- **最优先**：提高审计评分区分度（P1），使低质量输入获得显著更低的分数
- **其次**：修复 Smart Optimize 后的状态流转（P2）
- **再次**：增强搜索查询的上下文相关性（P2）
